## Overview

The communication layer of a 2D-parallel training pipeline, built from scratch directly on raw
MPI collectives rather than a higher-level distributed training library. It combines data
parallelism with tensor model parallelism — both a naive version and a Megatron-LM-style version
— and extends the setup with ZeRO-style optimizer-state sharding to cut memory usage.

## Problem

Training large models requires splitting both the *data* (data parallelism) and the *model
itself* (tensor model parallelism) across devices, then keeping every replica's gradients and
parameters correctly synchronized. Doing this efficiently means choosing the right collective
operation for each communication pattern, and — since every data-parallel replica otherwise
duplicates the full optimizer state — finding ways to shard that state without breaking
correctness.

## What I built

- A **naive tensor model parallelism** implementation, splitting layers across ranks.
- A **Megatron-LM-style tensor model parallelism** implementation, using the row/column-parallel
  linear layer split to minimize communication.
- A **data parallelism** layer synchronizing gradients across replicas.
- The combined **2D-parallel** setup (data parallelism × tensor model parallelism) running
  together over the same rank grid.
- **ZeRO-style optimizer-state sharding**, partitioning optimizer state across data-parallel ranks
  instead of duplicating it.
- The full communication layer built directly on **raw MPI collectives** via `mpi4py`
  (all-reduce, all-gather, reduce-scatter) rather than a pre-built distributed training framework.
- **Memory profiling** to verify the effect of ZeRO-style sharding on per-rank memory usage.

## Results

- A working 2D-parallel training pipeline (data parallelism + naive and Megatron-style tensor
  model parallelism) with correct gradient synchronization via hand-implemented MPI collectives.
- Verified memory reduction from ZeRO-style optimizer-state sharding relative to full-replication
  data parallelism.

## Trade-offs & limitations

- Implemented on raw MPI collectives for learning purposes rather than on top of a production
  library like DeepSpeed or Megatron-LM directly — real-world use would favor the battle-tested
  library.
